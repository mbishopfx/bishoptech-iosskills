# Apple SDK Framework Catalog

This catalog is a routing index, not an exhaustive API reference. Start with the user outcome and read the linked framework article before choosing an implementation. Availability, permissions, entitlements, and platform support must be checked for the target SDK.

For an outcome-first matrix that also records lifecycle, entitlement, adaptation, and proof boundaries, use the [capability-first Apple SDK atlas](10-capability-first-apple-sdk-atlas.md).

## Specialized iOS 26 route contracts

### App Intents and system intelligence

Use `AppIntent` for a typed app action, `AppEntity` for a discoverable app concept, and `EntityQuery` for resolving entities by identifier or options. Add `AppShortcutsProvider` only for intentionally curated, localized shortcuts. Treat every `perform()` path as a normal product command: validate parameters, current authorization, stale/deleted identifiers, account scope, and confirmation before mutations. Test from the app, Shortcuts, Siri/Apple Intelligence where supported, Spotlight, widgets, and a terminated process; system discoverability is not permission or side-effect proof.

### Widgets, controls, and Live Activities

Use `TimelineProvider`/`AppIntentTimelineProvider` for archived widget entries and refresh policies; `WidgetCenter` reload requests are hints, not immediate-render guarantees. Use `ControlWidget`, `ControlWidgetButton`, or `ControlWidgetToggle` only for small, repeatable actions/value projections that can finish inside the system extension boundary. Use `ActivityAttributes`, `Activity`, and `ActivityConfiguration` for a bounded Live Activity state machine; ActivityKit updates/pushes are a different mechanism from WidgetKit timelines. Model stale, ended, denied, extension-terminated, locked-device, push-token, and server-reconciliation states.

The operating system owns the outer treatment of these surfaces. Use `containerBackground(for: .widget)`, `widgetRenderingMode`, `widgetAccentable`, and image rendering policies so widgets adapt to tinted/clear Home Screens and Liquid Glass. Do not draw a duplicate full-screen glass shell inside a widget or control. Put on-device AI behind a typed proposal, current-state validation, optional review, and committed projection; never make a system-surface renderer the model or domain source of truth.

### Accessibility and alternate input

Treat standard SwiftUI controls as semantic contracts before introducing custom drawing. Verify labels, values, traits, grouping, `AccessibilityFocusState`, `DynamicTypeSize`, `accessibilityReduceMotion`, reduced transparency, contrast, hit regions, VoiceOver, Voice Control, Switch Control, keyboard/controller input, and non-color/non-gesture alternatives. `performAccessibilityAudit(for:)` is a diagnostic gate, not proof of a good reading order or an accessible physical workflow.

### Testing, performance, and release evidence

Use SwiftUI previews and deterministic fixtures for state rendering; XCTest/Swift Testing for domain and async behavior; XCUIAutomation for repeatable system flows; XCTest performance metrics such as `XCTClockMetric`, `XCTMemoryMetric`, `XCTHitchMetric`, and `XCTOSSignpostMetric` for controlled regressions; and MetricKit/signposts for real-device diagnostics and aggregate power/performance observations. Test release builds separately from Debug. A preview, simulator, unit test, performance baseline, or local StoreKit configuration cannot prove physical hardware, Apple Intelligence availability, system-surface delivery, production signing, App Store metadata, or release readiness.
