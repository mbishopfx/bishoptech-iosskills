# Framework Availability and Device-Proof Matrix

This matrix answers a question the framework catalog intentionally leaves open: “What can I call, what must I check at runtime, and what kind of evidence proves the route?” It is a planning aid, not a promise that every symbol is available on every iPhone or that a simulator can reproduce hardware behavior.

Refresh the linked Apple documentation before implementation. Record the target SDK, deployment target, device family, OS version, language/region, account state, capabilities, entitlements, and evidence level for the specific app.

## Availability vocabulary

| Label | What it means | What it does not prove |
| --- | --- | --- |
| Documented | An official Apple or Swift page describes the framework, API, or behavior. | That the target project has the required SDK or configuration. |
| Compile | The selected SDK accepts the source and the target builds. | That the API is available on the minimum OS or that a device can perform the work. |
| Runtime API | Swift availability checks or framework-specific availability APIs select a path for the running OS/device. | Permission, hardware, model readiness, account, network, or entitlement state. |
| Service/device state | The app checks authorization, hardware, model readiness, paired accessory, language asset, network, or account state. | A successful check in one fixture proves all users or devices work. |
| System-surface proof | The real widget, notification, shortcut, extension, Watch, CarPlay, App Clip, or share destination is invoked and behaves correctly. | App-screen correctness alone. |
| Release proof | A signed Release/TestFlight/App Store build is exercised in a user-like environment. | Production health, review approval, or every device/OS combination. |

Swift’s `#available` and `@available` mechanisms address platform/API availability. They are not a universal hardware or permission test. Apple’s Xcode guidance also distinguishes simulated from physical devices and calls out hardware-specific features as requiring a physical device test.

## Evidence ladder

1. **Source review:** link the exact official page and note any “availability,” “supported devices,” “requires capability,” “requires permission,” or “in development” language.
2. **Target inspection:** record the deployment target, SDK/toolchain, target memberships, supported destinations, Info.plist usage descriptions, capabilities, entitlements, and package/model resources.
3. **Compile/test:** build the selected target and run unit, integration, preview, or fixture tests for deterministic behavior.
4. **Simulator:** exercise layout, navigation, fakeable data, permission branches, and system-surface layout where the simulator supports the surface. Label hardware and service behavior as simulated.
5. **Physical device:** test camera, microphone, sensors, GPU/thermal behavior, haptics, biometric state, Apple Intelligence/model readiness, protected data, paired accessories, and real system surfaces on representative devices.
6. **Signed/release environment:** test capabilities, provisioning, App Store Connect configuration, TestFlight, production-like network/service accounts, and release configuration separately.

The evidence level should be attached to the claim. “The source documents VisionKit” and “this target’s live scanner works on an iPhone 17 running the selected OS” are different statements.

## Specialized privacy, test, performance, accessibility, and release gates

### Privacy manifest is a bundle/configuration artifact

Treat these as related but separate records:

| Record | What it describes | Verification boundary |
| --- | --- | --- |
| `PrivacyInfo.xcprivacy` | Data collection, tracking domains, and required-reason API categories for the app or SDK bundle | Inspect each executable/framework/SDK resource in the built artifact; a source file that is not target-owned or bundled does not prove the shipped manifest. |
| `NSPrivacyAccessedAPITypes` | The required-reason API categories used by that app or SDK | For each category, select only Apple-approved reason values that match the actual user-facing functionality; never invent a reason string or use the manifest to authorize tracking. |
| `NSPrivacyCollectedDataTypes` | Data types collected by the app or third-party SDK, including linkage, tracking, and purposes | Reconcile the manifest and SDK manifests with actual network/retention behavior and App Store Connect privacy answers. |
| App Store Connect App Privacy | The public-facing data-practice answers and privacy-policy URL | Publish and recheck the product-page disclosure; an accurate manifest does not automatically prove accurate App Store Connect answers. |

Required-reason API policy applies to code in third-party SDKs as well as app code. An app manifest cannot stand in for an SDK’s own manifest. Use the exact keys and approved values from [Privacy manifest files](https://developer.apple.com/documentation/bundleresources/privacy-manifest-files), [Describing use of required reason API](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api), and [Describing data use in privacy manifests](https://developer.apple.com/documentation/bundleresources/describing-data-use-in-privacy-manifests). Generate the archive privacy report and compare it to the App Store Connect record before calling the privacy surface consistent.

### Testing route and test-plan state

Use the testing system that matches the claim:

| Claim | Preferred route | State to record |
| --- | --- | --- |
| Pure domain or model transformation | Swift Testing `@Test`, suites, traits, and parameterized arguments | Input fixture, expected invariant, OS/SDK, and whether the test is deterministic. |
| UI behavior and assistive technology semantics | XCTest/XCUIAutomation and accessibility audits | Launch state, target device, permissions, accessibility settings, and test-result bundle. |
| Performance regression | XCTest performance metrics, `XCTHitchMetric`, `OSSignposter`, and Instruments | Warm/cold state, device, build configuration, workload, iteration policy, and baseline. |
| A set of tests for development or release confidence | Xcode `.xctestplan` | Included/excluded tags, configurations, diagnostics policy, destination, and command used to run it. |
| System or protected-service behavior | A test plus the real system surface/device/service | Account, permission, entitlement, server/push state, process state, and physical-device evidence. |

Swift Testing and XCTest can coexist in one test bundle. A green test-plan result is evidence only for the selected targets/configurations and does not establish that an unselected system surface or physical capability works. Xcode’s test-plan documentation describes separate plans for fast feedback and pre-submission coverage; preserve that distinction in the app record.

### OSLog, signposts, and MetricKit are different measurement layers

- Use `Logger` with a reverse-DNS subsystem and stable category names for useful diagnostics. Mark sensitive values with appropriate privacy formatting and do not log prompts, health data, raw images, credentials, or tokens merely to make a failure easier to reproduce.
- Use `OSSignposter` intervals/events with a stable signpost name and a per-operation signpost ID for a local timeline in Instruments. A signpost measures an interval; it does not automatically prove a user-visible performance target.
- Use XCTest metrics such as `XCTClockMetric`, `XCTMemoryMetric`, `XCTHitchMetric`, and `XCTOSSignpostMetric` for controlled regression runs.
- Use MetricKit for system-collected reports from real user devices. On an iOS 26 target, inspect the deployment target and current SDK before choosing the API: Apple documents `MXMetricManager` for iOS 13+, while current documentation describes the Swift-first `MetricManager` async-sequence route for iOS 27 and later. Keep the route behind availability checks and do not silently substitute a future-only API into an iOS 26 build.
- Treat a debug Instruments trace, a single physical device, a daily MetricKit aggregate, and a production-wide performance claim as different evidence levels.

### Accessibility and alternate input need task evidence

An automated audit can identify diagnostic issues, but it cannot establish that a person can complete the app’s core tasks. Build a task matrix across supported device families and test VoiceOver, Voice Control, Switch Control, Assistive Access, Dynamic Type, increased contrast, reduced transparency, Reduce Motion, captions/transcripts, keyboard/pointer/controller input, and localization where relevant. Apple’s accessibility testing guidance specifically calls for physical-device testing for assistive technologies that are unavailable in Simulator. Record the task, settings, device, OS, observed reading/focus order, control names/values, and result.

### Release proof has ordered gates

Use this order when a feature crosses into distribution:

1. Source review and target availability.
2. Target membership, privacy resources, usage descriptions, capabilities, entitlements, and extension configuration.
3. Compile and deterministic tests in the selected scheme/test plan.
4. Simulator or preview evidence for adaptable UI and fakeable states.
5. Physical-device evidence for hardware, protected services, assistive technologies, and system surfaces.
6. Release-configuration/archive validation, including the final privacy report and metadata.
7. TestFlight or App Store Connect evidence, with production/server/APNs/account state recorded separately.

An archive or successful upload proves packaging/processing at that point in time. It does not prove App Review approval, a live production route, a server-side entitlement, or every supported device.

## Route record to copy into an app plan

For each selected route, record:

| Field | Required value |
| --- | --- |
| User outcome | One sentence describing what the person can accomplish. |
| Official source | Exact Apple/Swift page and research date. |
| Target | Platform, device family, deployment target, SDK/toolchain, and supported OS range. |
| Gates | API availability, permission, entitlement, account, hardware, language, network, and system-surface conditions. |
| Fallback | Manual, local, cached, deterministic, or alternate-framework path when the route is unavailable. |
| Proof plan | Source review, compile/test, simulator, physical device, signed/release, or production evidence. |
