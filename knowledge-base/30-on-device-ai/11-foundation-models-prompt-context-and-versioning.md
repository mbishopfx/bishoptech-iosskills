# Foundation Models Prompt, Context, and Versioning Engineering

Foundation Models becomes useful in an app when the language task is bounded, measurable, and connected to an honest product state. A fluent answer is not the same thing as a verified fact, a permitted action, or a committed record. Treat prompts, context, tools, schemas, model availability, validation, and user review as one versioned feature contract.

This page focuses on the iOS 26-era on-device route. Current Apple documentation can also describe later SDK symbols and model revisions; inspect the availability annotations in the selected Xcode SDK before using any newer API in an iOS 26 target.

## The request contract

Before writing a prompt, record the smallest useful contract:

| Field | Decision | Why it matters |
| --- | --- | --- |
| User outcome | What should the person accomplish? | Prevents a general chatbot from replacing a focused feature. |
| Model use case | Text generation, structured output, tool-assisted lookup, or multimodal understanding | Determines the framework route and evidence needed. |
| Trusted instructions | Stable role, task, constraints, and output boundary owned by the app | Keeps product rules separate from user or retrieved content. |
| Untrusted input | User text, imported files, tool output, OCR, transcript, or image-derived text | Must not be allowed to rewrite app authority or policy. |
| Output contract | Plain text, `@Generable` value, or a proposal envelope | Defines deterministic validation and review. |
| Side-effect boundary | No side effect, preview, or explicit approved domain action | A model/tool decision never substitutes for authorization. |
| Version | Prompt, schema, tool, fixture, app/build, SDK, OS, model/asset state | Makes regressions and model updates comparable. |

The feature should still have a useful manual or deterministic path when the model is unavailable, the input is unsupported, or the person rejects the proposal.

## Prompt anatomy

Apple’s prompting guidance emphasizes concise, specific instructions for a smaller on-device model. A practical prompt has four parts:

```text
TASK: one imperative sentence describing the bounded job
OUTPUT: exact fields or response shape the feature needs
RULES: short constraints, limits, and uncertainty behavior
SOURCE: clearly delimited user or app data, treated as reference material
```

Keep stable behavior in `Instructions` and request-specific material in `Prompt`. Use `PromptBuilder` when the prompt depends on app state, but avoid interpolating sensitive data that the feature does not need. Keep external content visibly delimited and state that it is data to analyze, not instructions to follow.

Prefer:

- one clear task over a long persona or policy essay;
- a small number of explicit constraints over vague quality language;
- bounded output fields over a prose answer that must be parsed later;
- a concise explanation or provenance field only when the user can benefit from it;
- splitting a complex task into smaller deterministic stages instead of asking one session to solve everything.

Do not use “confidence” language generated by the model as a substitute for evidence. If the product needs confidence, calculate or calibrate it from the actual route and show its limitations.

## Context is a finite product resource

Every interaction in a `LanguageModelSession` consumes context: instructions, prompts, tool definitions and results, generated schemas, and model responses. The session transcript retains the interaction history. A long conversation can therefore fail even when the latest prompt is short.

Use the selected SDK’s `contextSize` and token-counting APIs when available to measure the real route. Treat context budget as part of the feature design:

| Pressure | Safer response |
| --- | --- |
| Long source document | Chunk into independent sessions, summarize each chunk, then combine bounded summaries. |
| Large tool schema | Remove unused fields, shorten descriptions, split tools by task, or query deterministically before prompting. |
| Large generated schema | Limit array counts and field lengths; include only fields used in review or validation. |
| Long conversation | Start a fresh session with a minimal, approved summary and current domain revision. |
| Multilingual text | Measure token use per supported language; character count is not a universal token estimate. |
| Context overflow | Preserve the source and last confirmed result, show a recovery state, and retry with a new bounded context. |

`prewarm(promptPrefix:)` can reduce latency when there is a strong signal that a request will happen after a meaningful preparation window. It is a performance hint, not a readiness guarantee; do not call it immediately before every response or treat it as proof that the model is loaded.

## Session topology

Choose a session lifetime deliberately:

| Feature shape | Session choice | Risk to handle |
| --- | --- | --- |
| One-shot extraction or draft | New session per operation | Repeated setup cost; keep prompt/schema versions with the result. |
| Short conversational editor | Reuse one session while the person remains in the workflow | Transcript growth, cancellation, account switch, and sensitive retention. |
| Long document processing | Multiple short sessions plus deterministic aggregation | Loss of cross-chunk context and inconsistent summaries. |
| Resume after termination | Rehydrate only the minimum safe transcript/state | Stale source revision, privacy retention, and schema/prompt migration. |
| Shared or multi-account app | Session scoped to one authorized account/workspace | Never carry transcript or tool authority across an account switch. |

The transcript is an input to a future model request, not a canonical record. Store only what the product needs, redact or expire sensitive content, and keep domain state in the app’s persistence layer.

## Guided output and validation

`@Generable` and `@Guide` define a structured generation target. They improve the shape of the response but do not prove that the values are true, current, authorized, or safe.

Use a proposal envelope that carries evidence rather than replacing the domain object:

```swift
struct ModelProposal<Value: Sendable>: Sendable {
    let operationID: UUID
    let promptVersion: String
    let schemaVersion: Int
    let sourceRevision: String
    let generatedValue: Value
    let provenance: [SourceReference]
}
```

After generation, deterministic code should check:

- schema and field lengths;
- allowed enum/range/date values;
- source revision and current account scope;
- duplicate/conflict rules;
- authorization and business policy;
- required provenance or source coverage;
- whether the result is complete enough to show for review.

An invalid proposal should become a visible repair state, not an empty field silently substituted into a save operation.

## Tools are context and authority boundaries

Tool definitions, descriptions, parameters, and results all contribute to the session context. Keep tool names/descriptions precise and return the minimum data the model needs. A read-only tool can ground a response; a preview tool can calculate a proposed outcome; a mutation tool still needs a separate authorization and commit boundary.

Apple documents tool-calling modes such as allowed, required, and disallowed in current Foundation Models SDKs. If a route uses required tool calling, define an exit condition so the session can produce a final response instead of calling indefinitely. Confirm the exact options and availability for the selected SDK.

Use this rule:

```text
model chooses whether to call -> tool validates its own inputs/permissions
                           -> tool returns bounded data or preview
                           -> app validates proposal and asks the person
                           -> domain use case commits with idempotency
```

Treat tool output, retrieved documents, and external text as untrusted data. Never let a tool return hidden instructions that silently change the trusted task contract. Never log raw tool payloads, prompts, or transcripts merely to make evaluation convenient.

## Prompt and model versioning

Apple recommends comparing prompts against old and new model versions when the system model changes. Keep the following version tuple with every evaluation and user-visible proposal:

```text
app/build + SDK + OS/build + model availability/revision
+ prompt/instructions + schema/guides + tools + fixture/evaluator
+ locale + device/configuration + domain validation policy
```

Use a versioning strategy that fits the product:

- bundled prompt constants are simple but require an app update;
- localized string catalogs can version and localize prompt variants;
- a server-provided prompt can roll out or roll back faster, but it introduces network, signing, privacy, cache, and offline policy;
- availability checks can select a prompt variant for a known OS/model boundary, but they do not replace evaluation.

When the model changes, run the old and new prompt against the same fixtures. Compare schema validity, groundedness, omission/invention, refusal/safety behavior, tool calls, correction burden, context use, latency, and resource cost. A more fluent result is not an improvement if it increases unsafe proposals or makes the user correct more fields.

## Evaluation-driven development

Create evaluation scenarios while designing the feature, not after the prompt “looks good.” Start with a small set of critical cases, then expand by failure pattern:

1. define the user outcome and objective success criteria;
2. create representative, empty, ambiguous, long, multilingual, adversarial, private, lifecycle, and side-effect fixtures;
3. run the same prompt/schema/tool configuration across the fixture set;
4. score field-level correctness and safety, not just prose similarity;
5. inspect failures and change one variable at a time;
6. rerun the full set before accepting a prompt or model change;
7. retain a redacted evidence record with the exact configuration.

The human review burden is a first-class metric. A feature that generates a polished draft but requires the person to rewrite every important field may be worse than a deterministic form.

## Privacy and claim boundary

On-device execution can reduce data movement, but it does not make a feature automatically private. Review transcript retention, app logs, analytics, imported content, tool/network access, indexed entities, backups, and account switching separately. If a route uses a different model or a system-owned surface, document that boundary plainly.

Use claims that match evidence:

| Evidence | Safe statement |
| --- | --- |
| API/source only | “The app is designed around Foundation Models.” |
| Compile in target | “This target compiles the selected Foundation Models route.” |
| Fixture evaluation | “This prompt passed the recorded fixture set under the named configuration.” |
| Physical device | “This configuration produced the observed latency/resource/availability result on the named device.” |
| System surface | “The named Siri/Spotlight/Shortcuts/system route was observed under the recorded configuration.” |

Do not collapse these into “the AI works everywhere,” “the model is always on device,” or “the feature is accurate.”

## Proof matrix

| Concern | Required evidence |
| --- | --- |
| Prompt/schema API | Current source page, selected SDK signature, macro expansion where relevant, compile result. |
| Context budget | Token-count/context-size measurement, long-input fixtures, overflow recovery, and session/transcript policy. |
| Prompt update | Old/new model comparison, versioned fixtures, regression thresholds, and rollback decision. |
| Tool boundary | Tool parameter validation, authorization, bounded output, required-mode exit, cancellation, and side-effect tests. |
| Privacy | Redaction/retention/logging review, account-switch test, manifest/configuration review, and network observation where applicable. |
| User outcome | Review/edit/reject/commit task completion and correction burden on representative fixtures. |
| Runtime behavior | Named physical device, OS/build, language, Apple Intelligence setting, latency, memory, thermal, and battery evidence. |
